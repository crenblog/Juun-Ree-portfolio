# All Work — 탐색 UX와 공간 전환 리서치

작성: 2026-09-22 · 초기 조사/제안 기록

> 최신 구현 여부는 [구현 현황과 남은 작업](all-work-implementation-status.md)을 기준으로 본다. 이 문서 아래의 ‘미구현’ 표기는 초기 조사 당시 상태다. 이후 일시정지, 가장자리 힌트, fragment 섹션 연결, 관련 카드 강조, 공간 전환과 복귀 보존을 구현했다. 실제 프로젝트 증거 이미지로의 교체와 실기기 검증은 남아 있다.

## 최신 사용자 피드백 반영 — 연속 이동이 우선

아래 문서의 초기 터치 정렬·정지 제안은 사용자의 후속 피드백으로 철회했다. 실제 구현은 나선의 감기는 방향을 반전하고, 아래로 스크롤/위로 스와이프할 때 카드가 **위로** 이동한다. 자동 이동도 같은 경로와 방향을 따른다. 카드별 스냅, 중앙 통과 시 감속, 호버 정지는 적용하지 않는다. PC 호버 캡션과 터치의 고정 위치 정보는 유지하되 흐름을 막지 않는다. 이전/다음 버튼은 사용자가 명시적으로 선택한 경우에만 한 항목씩 이동한다. 모션 감소 설정 및 키보드 포커스의 읽기 보호는 예외로 유지한다. 전환 애니메이션과 추가 탐색 구조는 여전히 제안 단계다.

## 먼저 결론

이 페이지의 역할은 ‘9장의 이미지가 도는 갤러리’보다 **내 생각과 작업의 일부를 골라 꺼내 보는 아카이브**에 가깝다. 따라서 다음 개선은 3D 효과 추가가 아니라, **무엇을 보고 있는지 → 무엇과 연결되는지 → 어디로 들어가는지 → 어디로 돌아오는지**를 명확히 만드는 것이다.

이번에 구현한 범위:

- 나선 감김 방향 반전. 앞으로 스크롤할 때 위로 이동하며 자동 이동도 같은 방향이다. 이전/다음 버튼과 방향키는 작업 순서라는 의미를 유지한다.
- 나선의 항목당 상승량을 카드 높이의 55% → 40%로 조정(약 27% 축소). 짧은 화면의 최소값은 .48 → .36.
- PC: 상시 중앙 캡션 제거. 카드 진입 지점 근처에 작은 제목·분류 표시. 이동은 계속하고 캡션 위로 이동해도 정보 유지. 키보드 포커스에서도 표시하고 Escape로 닫기.
- 터치: 중앙 항목의 제목·View project와 이전/다음 버튼을 하단의 안정된 위치에 표시. 스냅 없이 스크롤·자동 이동이 계속 이어진다.
- 기기 이름이나 화면 너비만으로 판단하지 않고 hover/pointer 능력과 실제 포인터 입력으로 모드를 결정.

이번에 구현하지 않은 범위:

- 메인 ↔ All Work ↔ 상세 전환 애니메이션.
- 콘텐츠 구조 변경, 새 필터·목록·연결선·설명문 추가.
- 실제 프로젝트 이미지로 교체하거나 성과·역할을 새로 작성하는 일.

## 조사 범위와 신뢰 수준

‘상위 1%’는 검증 가능한 UX 기준이 아니다. 수상은 미적·제작 완성도의 참고 신호이며, 탐색 성공률이나 접근성을 보증하지 않는다. 수상 주체가 **개인인지, 그 사람의 작업인지, 포트폴리오 사이트 자체인지**도 구분해야 한다.

이번 조사는 제작자 본인의 설명, 공식 수상 페이지, 실제 사이트의 공개 콘텐츠, W3C 지침과 현재 코드 점검을 기반으로 한다. 브라우저 연결이 두 차례 타임아웃되어 레퍼런스의 현재 애니메이션을 직접 재생·프레임 측정하지는 못했다. 아래의 모션 시간과 연결 연출은 관찰 결과가 아니라 **우리 사이트를 위한 설계 제안값**이다.

### 수상 사례에서 읽을 수 있는 공통점

위 사례를 ‘모두 같은 방식’이라고 일반화할 수는 없다. 다만 우리에게 유효한 판단은 다음이다.

1. **하나의 시각 언어가 상태 변화에도 이어져야 한다.** Haoqi의 제작기에서 직접 뒷받침되는 원칙이다.
2. **형태와 내용의 역할을 나눠야 한다.** 아카이브는 발견을, 상세는 역할·판단·결과를 담당하도록 한다. 이는 Jesse/Alex의 공개 콘텐츠에서 얻은 해석이다.
3. **화려한 진입보다 복귀의 정확성이 중요하다.** 아래의 상태 복원은 우리 구현에 대한 제안이며 모든 수상 사이트에서 관찰한 공통 사실이 아니다.

## 터치 화면: 왜 고정 캡션인가

호버를 모바일의 ‘첫 탭’으로 바꾸면, 방문자는 첫 탭이 선택인지 열기인지 배워야 한다. 이 갤러리에는 이미 회전·깊이·반복이라는 낯선 요소가 있다. 추가로 이중 탭 규칙까지 숨길 이유가 없다.

선택한 방식:

- 스와이프 / 이전·다음 버튼으로 탐색.
- 카드가 중앙을 지나면 이름과 `View project`를 같은 하단 위치에서 읽는다. 카드 위치는 강제로 정렬하지 않는다.
- 카드 또는 명시적인 링크를 한 번 탭하면 상세를 연다. 별도의 ‘한 번 선택, 한 번 더 열기’ 규칙은 두지 않는다.
- 사용자 요청에 따라 터치에서도 흐름을 유지한다. 이름은 고정된 위치에 표시하고, 누르기 시작한 작업을 기억하여 탭 도중 중앙 항목이 바뀌어도 다른 작업을 열지 않게 한다. 지속 회전의 접근성을 위한 명시적 정지 제어는 별도의 후속 검토 사항이다.
- 버튼은 최소 폭 44px로 설계했다. 이는 이번 디자인의 여유 있는 목표이며 WCAG AA 최소값을 44px라고 주장하는 것은 아니다. [W3C Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

이 3D 갤러리가 전형적인 슬라이드쇼와 같지는 않지만, 이동하는 대상을 직접 통제하게 하고 포커스 중 읽기를 방해하지 않는다는 원칙은 [W3C Carousel 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/carousel/)을 참고했다. PC 호버 캡션의 유지·접근·닫기는 [W3C Content on Hover or Focus](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html)를 참고했다. 이것만으로 사이트 전체의 접근성 준수를 인증하는 것은 아니다.

## PC 진단 — 먼저 고쳐야 할 것

### P0. ‘9 works’의 의미가 실제 데이터와 다르다

현재 `rings-data`에는 9개 카드가 있지만 목적지는 `biennale`, `loop`, `off` 세 개다. 9개의 독립 프로젝트처럼 세면 기대와 도착지가 어긋난다. 현재 반복 풀은 같은 9개를 더 렌더링하므로 오해가 커질 수 있다.

두 방향 중 선택이 필요하다. 이번에는 콘텐츠를 임의로 바꾸지 않았다.

- **프로젝트 중심:** 대표 카드 3개만 작업으로 세고 나머지는 실험/장면으로 구분.
- **생각의 아카이브 중심 — 추천:** 9개를 `Fragments` 또는 `Entries`로 취급. 호버에는 `Loop — Recall Rhythm`처럼 부모 작업을 보여주고 상세의 관련 섹션으로 연결. 계수는 `03 / 09 entries · 3 projects`처럼 정확히 표시하되 화면 복잡도를 보고 축약.

### P0. 커버와 실제 상세 사이의 연결

현재 일부 사진은 무료 스톡, 일부 SVG는 설명용으로 구성한 이미지다. 갤러리 사진도 실제 SeMA 현장 사진이 아니다. 상세로 확대 연결할 때 표지와 히어로가 다르면 동일한 물체라는 인상이 끊어진다. 전환 구현 전에 실제 화면·리서치 산출물·프로토타입 캡처로 콘텐츠를 정리해야 한다. 출처는 `docs/work-gallery-assets.md`에 기록되어 있다.

### P1. 자동 움직임에 대한 명시적 통제

PC는 현재 키보드 선택 중 정지하지만, 별도의 영구 일시정지 버튼은 없다. 기본 흐름은 유지하되 사용자가 원할 때만 끄는 작은 제어를 후속 검토할 필요가 있다. 모션 감소 설정에서는 정지한다. 이는 장식 추가가 아니라 읽기 시간의 통제다. [W3C Pause, Stop, Hide](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)

### P1. 바로 찾는 경로

공간 탐색은 발견에는 좋지만 특정 프로젝트를 빨리 재방문하기에는 느리다. 작고 선택적인 `Index`를 열면 실제 프로젝트 이름만 보이는 목록을 제안한다. 기본 화면을 목록으로 바꾸거나 이미 제거한 모드 토글을 되살리는 뜻은 아니다. 사용자가 열었을 때만 나타나는 보조 경로이며 아직 미구현이다.

### P1. 작은 뒤쪽 카드의 의미와 클릭 영역

전경은 읽고 선택하는 대상, 뒤쪽은 연결된 기억의 존재를 알리는 대상으로 분리하는 편이 낫다. 현재 GPU 그림과 DOM 클릭 표면이 별도 레이어여서 겹친 카드의 가림 순서·선택 정확성을 추가 점검해야 한다. 뒤쪽을 무조건 전경과 같은 클릭 대상으로 두면 작은 목표와 겹침 문제가 생길 수 있다.

### P2. 힌트의 위치

처음 중앙의 SCROLL 배지가 이미지를 덮는다. 다음 단계에서 화면 가장자리의 짧은 `Scroll to explore`로 옮기고 첫 조작 후 숨기는 안을 권한다. 긴 콘셉트 설명은 넣지 않는다.

## 페이지 전환 — 구현 전 제안

### 현재 코드의 실제 구조

`jrOpenCase()`는 상세를 읽어 `.case-view`로 열고 `history.pushState()`로 주소를 바꾼다. 성공 경로에서는 항상 전체 페이지를 새로 로드하는 것이 아니다. 반면 직접 상세 URL로 진입하거나 읽기에 실패하면 문서 이동이 발생한다. 현재 기본 효과는 불투명도와 약한 Y 이동이라 ‘같은 카드가 펼쳐졌다’는 물체의 연속성이 없다.

즉, 지금 필요한 것은 SPA 프레임워크로 전면 재작성하는 일이 아니라 **같은 문서에서 열리는 경로 / 실제 문서가 바뀌는 경로 / 브라우저 뒤로가기**를 같은 규칙으로 연결하는 일이다.

| 카드 확대 → 상세 히어로 | 고른 작업 한 장을 공간에서 꺼내 펼침 | 출발 물체를 추적하기 쉬움. 같은 실제 이미지와 복귀 상태가 필요 | **All Work → 상세에 추천** |
| 동일 색 면의 짧은 와이프 / 페이드 | 같은 브랜드의 다음 장면으로 이동 | 구현·실패 복구가 단순하지만 공간의 연결은 약함 | 직접 진입·지원 불가 환경의 대안 |
| 카메라가 원통 안으로 깊게 비행 | 머릿속 공간으로 진입하는 연출 | 첫인상은 강하지만 읽기 지연·멀미·성능 위험 | 기본 이동에는 비추천. 나중에 짧은 진입 실험만 |

### 추천 전환 문법: 꺼내기 → 펼치기 → 돌려놓기

아래 시간은 수상 사이트 측정치가 아니라 첫 프로토타입용 제안값이다.

**메인 → All Work / 약 450–550ms**

- 메인의 아이보리와 상단 위치를 시각적 기준점으로 유지.
- 대표 이미지 한 장을 연결할 수 있다면 그 이미지를 전경 카드로 남기고 주변 카드·그리드가 점차 드러남.
- All Work 링크처럼 특정 이미지가 없는 진입은 억지로 임의의 카드를 변형하지 않고, 기존 면이 넓어지며 공간이 열리는 짧은 전환 사용.
- 첫 프레임에 캔버스 초기화·텍스처 로딩이 끼어들지 않도록 준비 완료를 확인. 준비가 늦으면 즉시 정상 화면 이동.

**All Work → 상세 / 약 380–500ms**

- 누른 카드의 이미지·현재 화면 사각형·프로젝트 ID·반복 회차의 절대 sequence·progress를 보관.
- 회전을 멈추고 카드가 정면으로 펴지며 상세 첫 이미지 영역으로 확장.
- 주변 공간은 약하게 사라지고, 제목·역할은 이미지 도착 직후 짧게 나타남.
- 한 번에 크게 움직이는 주인공은 카드 하나. 카드 휘어짐·글리치·긴 로더는 사용하지 않음.

**상세 → All Work / 약 300–400ms**

- 원래 눌렀던 동일한 반복 회차·각도로 복귀. 무조건 첫 프로젝트부터 시작하지 않음.
- 캡션·포커스도 원래 작업으로 복원. ‘내가 꺼냈다가 돌려놨다’는 인식의 핵심.
- 상세에 직접 진입하여 출발 카드가 없으면 가짜 역재생을 만들지 말고 일반적인 All Work 진입으로 처리.

### 기술 선택의 방향 — 아직 적용하지 않음

- 현재 오버레이 경로: 같은 문서 내 View Transition 또는 명시적인 이미지 복제 레이어로 출발/도착 연결.
- 실제 `index.html` ↔ `work.html` 문서 이동: 같은 출처의 페이지가 함께 참여하는 cross-document View Transition을 점진적으로 적용 가능. 지원되지 않는 환경은 정상 링크 이동 유지. [Chrome 공식 문서](https://developer.chrome.com/docs/web-platform/view-transitions/cross-document), [MDN](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API)
- 반복 카드 전부에 같은 전환 이름을 주면 안 됨. 선택한 한 occurrence에만 고유 이름을 부여.
- WebGL 카드의 DOM 이미지가 숨겨져 있으므로, DOM만 전환 대상으로 지정하면 이미지가 빠질 수 있음. 클릭 순간의 이미지 레이어를 명시적으로 만들어 GPU/DOM 간 화면 위치를 맞추는 검증 필요.
- 새 탭 열기, 직접 URL 진입, 새로고침, 느린 네트워크, 이미지 로드 실패, 뒤로/앞으로, 연속 클릭을 기본 기능으로 보장.
- `prefers-reduced-motion`이면 이동/확대 없이 즉시 또는 짧은 페이드. 브라우저별 지원은 구현 시 실제 타깃 환경으로 재검증.

## ‘머릿속 데이터베이스’를 더 명확하게 만드는 방법

**공간만으로는 ‘머릿속’보다 ‘3D 전시장’으로 읽힐 가능성이 있다.** 뇌 모형이나 긴 설명이 아니라 내용과 반응이 이를 전달해야 한다. 다음은 디자인 가설이지 사용자 테스트 결과가 아니다.

1. **기억의 단위를 만든다.** 최종 결과 화면만 반복하지 말고 실제 문제 메모·설계 선택·프로토타입·출시 결과를 서로 다른 fragment로 구성한다. 사실 확인된 자료만 사용.
2. **관련성을 선택 순간에 드러낸다.** Loop 카드에 호버하면 같은 프로젝트의 다른 fragment가 살짝 선명해지는 정도. 거미줄 같은 상시 연결선은 피한다.
3. **내가 고른 것이 전경으로 나온다.** 탐색 때는 카드가 계속 흐르고, 이름은 안정된 위치에서 읽는다. 사용자가 상세를 열었을 때만 그 작업을 펼친다. 개별 카드마다 정지시키지 않는다.
4. **상세는 새로운 사이트가 아니라 그 생각의 확대본이다.** 관련 장면으로 들어가고, 원래 공간으로 정확하게 돌아온다.
5. **고정 기준점을 남긴다.** 아이보리, 작은 녹색 UI, 일관된 이름/번호는 고정. 공간과 카드만 이동해야 관찰자의 자리가 느껴진다.
6. **한 문장은 필요할 때만.** 긴 소개 대신 메인의 All Work 링크 근처에 `Inside my work` 같은 짧은 선택지를 검토. 현재 All Work의 ‘작업만 보이기’ 원칙은 유지.

START/END 원은 사이클 경계이지 프로젝트 수를 늘리는 장식이 아니다. 앞·뒷면 표시는 유지하되, 이를 이해하지 않아도 이전/다음과 상세 진입을 사용할 수 있어야 한다.

## 다음 실행 순서

1. **콘텐츠 단위 결정:** 3 projects / 9 fragments 중 무엇을 어떻게 표시할지 확정. 실제 이미지와 상세 목적지 매핑.
2. **탐색 검증:** PC hover, 터치 연속 이동/명시적 열기, 반복 경계, 확대·텍스트 가독성. 선택적 정지 제어와 빠른 Index는 추가 승인 후.
3. **전환 1개만 프로토타입:** All Work → 한 상세 → 같은 위치 복귀. 성공하면 메인에도 같은 문법 확장.
4. **콘셉트 검증:** 5명 정도에게 설명 없이 ‘이 공간은 무엇 같나’, ‘Loop를 찾아 열고 돌아와보라’를 요청. 이는 탐색적 검증이며 통계적 증명은 아님.
5. **성능·복귀·모션 감소 검증 후 전면 적용.**

프로토타입 합격 기준 제안: 10초 내 조작 방법 이해, 두 번 이내의 명시적 조작으로 원하는 상세 진입, 돌아왔을 때 같은 작업 식별, 드래그 후 오클릭 없음, 모바일에서 움직이는 대상을 쫓지 않고 읽고 누를 수 있음. 수치는 우리 프로젝트의 검증 목표이며 업계 공통 기준이 아니다.
