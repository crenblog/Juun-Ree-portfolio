# 포트폴리오 정보 구조 · 화면 구성 로드맵

작성일: 2026-09-21  
목적: **작업의 완성도를 먼저 보여 주고, 그 다음에 판단과 과정을 증명하는 포트폴리오**로 재구성한다.

## 0. 한 문장 원칙

방문자는 첫 10초 안에 다음을 알아야 한다.

> Juun은 어떤 제품 문제를 해결하는 디자이너이고, 실제로 무엇을 만들었으며, 어떤 결과를 만들었는가.

현재 사이트의 강점인 차분한 에디토리얼 톤과 `complexity → confidence` 관점은 유지한다. 다만 철학이 프로젝트보다 먼저 오래 머물지 않도록 한다. **메인은 결과를 보여 주는 곳, 상세는 판단을 증명하는 곳, All work는 작업의 범위를 보여 주는 곳**으로 역할을 나눈다.

## 1. 최종 정보 구조

```text
Home
├── Positioning + 대표 제품 이미지
├── Selected work (3개)
├── Working principles (짧게)
├── About / availability
└── Contact

All work
├── Featured case studies (3개)
├── Selected experiments / shipped fragments (있을 때만)
└── Contact

Case study
├── 30초 요약
├── 문제와 제약
├── 핵심 판단
├── 최종 제품 흐름
├── 검증 및 결과
└── 회고 + 다음 작업
```

### 콘텐츠 분류 규칙

| 구분 | 기준 | 보여 주는 방식 |
| --- | --- | --- |
| Featured case study | 문제·역할·결과·실제 화면을 모두 설명할 수 있는 작업 | Home, All work, 긴 상세 페이지 |
| Selected project | 결과는 있으나 이야기의 길이가 짧은 작업 | All work 카드 + 짧은 상세 또는 외부 링크 |
| Experiment / build | 탐색, 프로토타입, 개인 제작물 | All work의 별도 섹션. 케이스 스터디와 같은 무게를 주지 않음 |
| 비공개/미완성 | 보여 줄 증거가 부족한 작업 | 공개하지 않음 |

`All work`는 “10개를 채워 보이는 아카이브”가 아니다. 현재로서는 **Featured 3개만 있는 것이 더 설득력 있다.** 작업이 충분히 쌓일 때만 두 번째 섹션을 연다.

## 2. 화면별 전달 방식

## Home — 제품을 먼저 보여 주는 첫인상

### 목표

스크롤을 시작하지 않아도 역할, 관점, 대표 제품 하나를 동시에 인지시킨다. 현재의 큰 카피만 있는 Hero를 `카피 + 대표 제품 비주얼` 구조로 바꾼다.

### 권장 레이아웃

```text
Desktop
┌──────────── sidebar ───────────┬──────── main ───────────────────────┐
│ JUUN REE                       │ Product Designer · Seoul / Tokyo   │
│ short positioning              │ 큰 한 줄 포지셔닝                  │
│ Work / About / Contact         │ 2줄 설명 + 역할 범위               │
│                                │                                    │
│                                │ [대표 프로젝트의 실제 UI/제품 이미지]│
├────────────────────────────────┼────────────────────────────────────┤
│                                │ Selected work                      │
│                                │ 01 이미지 + 제목 + 역할 + 결과      │
│                                │ 02 이미지 + 제목 + 역할 + 결과      │
│                                │ 03 이미지 + 제목 + 역할 + 결과      │
└────────────────────────────────┴────────────────────────────────────┘

Mobile
Positioning → 대표 제품 이미지 → Selected work 카드 3개 → About → Contact
```

### Hero 구성

1. **Eyebrow:** `Product Designer · Seoul / Tokyo`
2. **Headline:** 사람의 망설임과 혼란을 줄이는 제품을 설계한다는 한 문장
3. **Proof line:** `Research, UX/UI, prototype & build` 또는 실제 강점 3개
4. **Featured visual:** SeMA의 실제 첫 화면 또는 40/90/180분 선택 흐름. 목업 장식보다 제품 화면이 우선이다.
5. **Caption:** `Biennale Guide — SeMA · Prototype test: 3/10 → 9/10 task completion`

Hero의 긴 설명과 펼침 인터랙션은 `How I work` 섹션으로 이동하거나 2문장으로 줄인다. 숨겨진 카피를 발견해야만 핵심을 이해하게 만들지 않는다.

### Selected work 카드 규격

모든 Featured 작업은 같은 정보 순서를 쓴다.

```text
[16:10 또는 4:3 실제 제품 이미지]
01 · 2025 · Mobile web
Biennale Guide — SeMA
One-line outcome / problem statement
Role · scope · evidence
Read case study →
```

- 카드 전체가 링크여야 한다. 모바일에서 호버 전용 프리뷰에 의존하지 않는다.
- 이미지에는 제품의 가장 중요한 한 장면을 쓴다. 장식용 추상 이미지나 동일한 색 면은 사용하지 않는다.
- 첫 카드만 조금 크게, 나머지는 동일한 크기의 2열(데스크톱) 또는 세로 카드(모바일)로 둔다.
- 수치가 있다면 설명보다 먼저 작은 강조 요소로 보여 준다. 단, 실제 출시 수치가 아니라면 `Prototype test · n=10`을 함께 표기한다.

### Home에서 하지 않을 것

- 빈 `All work` 페이지로 보내지 않는다.
- About을 긴 자기소개로 만들지 않는다.
- 각 프로젝트의 모든 과정을 적지 않는다.
- 이미지 없이 글자 크기만으로 제품 완성도를 설득하려 하지 않는다.

## All work — 넓이가 아니라 선택 기준을 보여 주는 페이지

### 목표

방문자가 “이 디자이너가 어떤 종류의 일을 어느 깊이로 할 수 있는가”를 30초 안에 훑는 인덱스다. Home의 단순 반복이 아니라, 선택의 범위를 보여 주되 사례의 밀도를 낮추지 않는다.

### 현재 결정

현재 `work.html`의 빈 본문과 04–10 템플릿 슬롯은 공개하지 않는다. 실제 콘텐츠가 없으면 `All work` 링크 자체를 잠시 숨기거나, Featured 3개만으로 완성된 인덱스를 만든다.

### 권장 레이아웃

```text
All work
짧은 소개: Products made for moments where people need clarity.

FEATURED CASE STUDIES
┌───────────────────────────┬───────────────────────────┐
│ 큰 이미지                  │ 큰 이미지                  │
│ Biennale Guide — SeMA      │ Loop — Vocabulary          │
│ Role · surface · outcome   │ Role · surface · outcome   │
└───────────────────────────┴───────────────────────────┘
┌───────────────────────────┐
│ Off — Screen Time          │
│ 이미지 + 역할 + 한 줄 결과 │
└───────────────────────────┘

MORE EXPLORATIONS  (작업이 3개 이상 준비된 뒤에만 추가)
작은 3열 카드: title / type / year / 1 line / external 또는 short case
```

### 카드 계층

| 계층 | 개수 | 정보량 | 상세 링크 |
| --- | ---: | --- | --- |
| Featured | 3개 | 이미지, 역할, 맥락, 결과 | 긴 케이스 스터디 |
| Exploration | 최대 6개 | 이미지, 유형, 한 줄 설명 | 짧은 페이지 또는 외부 링크 |

### 정렬·필터

처음에는 필터를 만들지 않는다. 6개 이하의 작업에서 필터는 편의보다 복잡성을 늘린다. 작업 수가 충분해질 때만 `Product / Research / Build` 정도의 단순 필터를 검토한다.

## Case study — 설득의 템플릿

### 목표

한 프로젝트를 처음 보는 사람이 30초, 3분, 10분 어느 시간대에도 필요한 정보를 얻는다. 긴 글을 읽는 사람과 결과만 확인하는 사람을 모두 수용한다.

### 공통 템플릿

```text
1. Case hero
   - Project type · year · client/context
   - Project title
   - 한 문장의 문제 / 왜 중요했는가
   - 실제 대표 제품 이미지 또는 짧은 제품 영상

2. At a glance  [30초 요약]
   - Role / team / duration / platform
   - Challenge
   - Outcome
   - Evidence label: Shipped / Prototype tested / Concept

3. The problem
   - 사용자와 조직이 처한 상황
   - 하나의 핵심 질문
   - 관찰·리서치 증거

4. The decision
   - 고려한 선택지 2–3개
   - 버린 것과 선택한 것
   - 선택 기준

5. The product
   - 핵심 흐름 3개
   - 각 흐름: 실제 화면 → 사용자 행동 → 설계 이유

6. Validation & outcome
   - 검증 방법, 참여자 수, 시점
   - 수치/관찰 결과
   - 알 수 없었던 점과 다음 검증

7. Reflection
   - 무엇이 유효했는가
   - 다음에는 무엇을 다르게 할 것인가

8. Next case / All work
```

### Case hero 레이아웃

```text
Desktop: 텍스트 5 : 대표 이미지 7의 2열
Mobile: 제목 → 요약 → 대표 이미지 → 결과 수치
```

- Hero에는 실제 제품 화면을 가장 크게 둔다. 지금의 SeMA 텍스트 Hero는 좋지만, 제품을 늦게 보여 준다.
- 수치는 `결과 + 검증 맥락`을 붙여 한 덩어리로 둔다.
  - 좋은 예: `3/10 → 9/10 task completion · moderated prototype test, n=10`
  - 피할 예: `3/10 → 9/10`만 독립적으로 크게 표기
- `Role / span / surface / context`는 본문 속 한 줄이 아니라, 스캔 가능한 2×2 메타 블록으로 고정한다.

### SeMA에 적용할 구체적 변경

| 현재 | 바꿀 방식 |
| --- | --- |
| 제목과 설명 뒤에 수치가 먼저 나옴 | 제목 옆에 실제 모바일 가이드 첫 화면을 배치 |
| 결과가 출시 성과처럼 먼저 읽힐 수 있음 | 수치 바로 옆에 `Prototype tested · n=10 · not launched` 표기 |
| Final Design에 CSS 폰 목업·인물 카드가 섞임 | 실제 UI 화면 3–5장으로 `Scan QR → choose time → follow route → find next work` 흐름 제시 |
| 긴 글을 순서대로 읽어야 함 | 상단 앵커: Overview / Decision / Product / Results |
| 강한 주장에 출처 맥락이 약함 | 리서치 근거, 관찰 표본, 가설을 구분해 라벨링 |

### 시각 규칙

- 본문 1–2블록마다 제품 화면, 도식, 관찰 기록 중 하나를 둔다.
- 이미지에는 반드시 설명 캡션을 붙인다. 예: `The first screen asks for available time, not a venue map.`
- 한 화면 안에서 가장 무거운 타이포그래피는 제목 또는 결과 하나만 사용한다.
- 인터랙션은 내용 이해를 돕는 경우에만 사용한다. 스크롤 애니메이션, 호버, 카드 전환은 증거를 가리지 않아야 한다.
- 모든 프로젝트가 같은 레이아웃을 쓰되, 대표 이미지의 비율·색·제품 맥락으로 개성을 만든다.

## 3. 제작 우선순위

## P0 — 구조를 확정한다 (먼저)

완료 기준: 어떤 페이지에 어떤 작업이 왜 있는지 결정되어, 비어 있는 화면이 공개 경로에 없다.

1. Featured 작업 3개를 확정한다: Biennale / Loop / Off.
2. 각 작업을 `Featured`, `Exploration`, `비공개`로 분류한다.
3. Home, All work, Case의 위 정보 구조를 와이어프레임으로 확정한다.
4. `work.html`을 Featured 3개 인덱스로 채우거나, 준비 전까지 Home의 All work 링크를 숨긴다.
5. 공통 케이스 템플릿의 섹션과 필수 입력값을 정한다.

산출물: 페이지별 와이어프레임, 프로젝트 인벤토리, 공통 케이스 콘텐츠 체크리스트.

## P1 — 실제 제품 증거를 준비한다

완료 기준: 세 Featured 프로젝트 모두 첫 화면에서 실제 제품을 볼 수 있다.

1. 프로젝트당 대표 이미지 1장과 흐름 이미지 3–5장을 선정·제작한다.
2. 모든 이미지에 모바일/데스크톱용 크롭을 만든다.
3. 각 프로젝트의 `문제 / 역할 / 제약 / 결과 / 검증 수준`을 1–2문장씩 작성한다.
4. 수치와 주장에 출처 또는 검증 맥락을 붙인다.

산출물: `assets/images/[project]/`의 커버·흐름 이미지, 프로젝트별 콘텐츠 시트.

## P2 — Home을 구현한다

완료 기준: 첫 화면에서 포지셔닝과 실제 제품 이미지를 함께 보고, 한 번의 스크롤 안에 대표 작업을 만난다.

1. Hero를 카피와 Featured visual의 2열/세로 구조로 변경한다.
2. Selected work를 이미지 중심 카드로 교체한다.
3. 모바일에서 이미지와 링크가 기본적으로 보이는지 확인한다.
4. 불필요하게 숨겨진 Hero 설명과 빈 All work 진입점을 정리한다.

## P3 — All work를 구현한다

완료 기준: Featured 3개가 한 화면 시스템 안에서 명확하게 비교되고, 비어 있는 슬롯이나 가짜 작업이 없다.

1. Featured grid와 카드 컴포넌트를 만든다.
2. 작업 수가 충분할 때만 More explorations 섹션을 추가한다.
3. 프로젝트 상세 이동과 브라우저 뒤로 가기 흐름을 검증한다.

## P4 — SeMA를 템플릿의 기준으로 재구성한다

완료 기준: 30초 요약, 실제 화면, 검증 수준, 핵심 판단이 빠짐없이 있고 다른 Featured 케이스가 같은 뼈대를 쓸 수 있다.

1. Case hero에 실제 제품 비주얼을 넣는다.
2. `At a glance`와 결과의 검증 라벨을 추가한다.
3. Final Design을 실제 UI 흐름으로 재구성한다.
4. 상단 앵커를 넣는다.
5. 이 구조를 `templates/case.html`에 반영한다.

## P5 — Loop, Off와 마감 품질을 맞춘다

완료 기준: 세 케이스가 같은 정보 품질과 다른 프로젝트 개성을 동시에 갖는다.

1. Loop, Off에 같은 템플릿을 적용한다.
2. EN/KR/JP에서 제목 줄바꿈, 메타 정보, 이미지 캡션을 점검한다.
3. 모바일 375px, 태블릿, 데스크톱에서 이미지 크롭과 카드 리듬을 점검한다.
4. 키보드 탐색, 명확한 링크 라벨, 감소된 모션 환경을 점검한다.

## 4. 작업을 시작할 때마다 쓰는 체크리스트

### Home 카드

- [ ] 실제 제품 화면이 보이는가?
- [ ] 제목만 읽고 문제와 제품 유형을 알 수 있는가?
- [ ] 내가 맡은 역할이 있는가?
- [ ] 결과 또는 검증 수준이 정직하게 적혀 있는가?
- [ ] 모바일에서 호버 없이 상세로 갈 수 있는가?

### Case study

- [ ] 첫 화면에서 제품과 핵심 문제를 함께 보는가?
- [ ] 30초 안에 역할, 기간, 플랫폼, 결과를 알 수 있는가?
- [ ] 의사결정의 대안과 기준이 있는가?
- [ ] 실제 UI 또는 프로토타입 흐름이 최소 세 장 이상 있는가?
- [ ] 수치가 무엇을, 어떻게 검증한 것인지 분명한가?
- [ ] 출시되지 않은 작업이라면 그 사실이 즉시 보이는가?
- [ ] 마지막에 다음 작업 또는 All work로 자연스럽게 이어지는가?

## 5. 이번 개편에서 지켜야 할 기준

1. **작업 수보다 증거의 밀도.** 3개의 깊은 사례가 10개의 빈 카드보다 강하다.
2. **이미지가 먼저, 설명은 그 다음.** 제품 디자이너의 포트폴리오는 제품을 보여 줘야 한다.
3. **수치는 항상 맥락과 함께.** 출시 결과, 프로토타입 테스트, 관찰 결과를 섞지 않는다.
4. **한 페이지에는 하나의 주된 행동.** Home은 케이스 읽기, All work는 작업 선택, 상세는 판단 이해.
5. **개성은 정보 전달을 방해하지 않는다.** 지금의 색·여백·타이포그래피 감도는 유지하되, 인터랙션은 발견성보다 명료성을 우선한다.
